## 2. プロジェクト背景・目的
### 2.1 背景
- AIエンジニアコース(スクール)の課題として、Trello風のタスク管理アプリを作る。
- 実在する顧客や発注者はいない。受講者本人が、依頼者・開発者・確認者を兼ねる。
- 仕事の進め方を学ぶため、実際の案件を想定した形式で要件定義書を作る。

### 2.2 目的
- **学習目的(主目的)**:要件定義から設計・実装・テストまでの一連の流れを経験し、システム開発の進め方を身につける。
- **成果物の目的**:Trello のような**カンバンボード形式**で、タスクの状態(未着手・作業中・完了)を視覚的に管理できるアプリを作る。
- やることをカードにして、列の間を動かし、進み具合を一目で分かるようにする。

### 2.3 学習で身につけたいこと
- 要件を整理し、文書にまとめる力
- 決めたことと決めていないことを区別して管理する力
- 要件とテストを対応づけて、完成を判断する力

## 3. システム概要
### 3.1 利用者・利用環境
- 利用者:自分1人(ログインや担当者の管理は不要)
- 環境:パソコンのブラウザ(Chrome など)のみ
- データの保存:実際のDBを使い、バックエンドを作る想定(2026-10-20 決定)。使う技術は[技術スタック候補](tech-stack.md)で今後決める。

### 3.2 機能の概要
3つの列(To Do / Doing / Done)にカードを並べ、追加・編集・移動(ドラッグ)・削除ができる。優先度の色分けと、期限切れの表示を行う。
詳細は[機能要件](functional-requirements.md)を参照。

### 3.3 用語
| 用語 | 意味 |
|---|---|
| ボード | 画面全体 |
| リスト(列) | To Do / Doing / Done の縦の列 |
| カード | 1つのタスク |

## 4. 対象外(今回は作らない)
列の追加・名前変更、担当者、ラベル、検索、複数人での共有、同じ列内でのカードの並び替え、削除したカードの復元。
これらの機能追加は、基本機能が完成した後に改めて検討する。

## 6. 決定事項
- カード削除時は確認ダイアログを出す(2026-10-12 決定)
- カード編集(F-09)を機能要件に含める(2026-10-14 決定)
- 新しいカードは列の一番上に追加する(2026-10-14 決定)
- 期限切れは期限の翌日からとする(2026-10-14 決定)
- 完了条件は「F-01〜F-09 がすべて動くこと」とする(2026-10-14 決定)
- 課題のゴールは設計までとし、完了条件を「納品物が揃い、F-01〜F-09 が設計に反映されていること」に変更する(2026-10-18 決定)
- 納期は期限なし、スクールへの提出は不要(2026-10-18 決定)
- 非機能要件は NF-01〜15 のとおり数値化する。想定カード枚数は200枚、反応時間は1秒以内、起動表示は3秒以内、対応は Chrome 最新版・幅1280px以上、初めての操作は5分以内(2026-10-19 決定)
- 入力の上限(タイトル50文字、説明文500文字)は仮の値とし、データ設計で正式に決める(2026-10-19 決定)
- 同じ列の中でのカードの並び替えは作らない。列をまたぐ移動のみとする(2026-10-19 決定)
- 削除したカードを元に戻す機能は作らない(確認ダイアログがその代わり)(2026-10-19 決定)
- 説明文の確認、カードの追加・編集・削除の操作方法は、画面設計書の「3. 決定事項」のとおりとする(2026-10-20 決定)
- 入力の上限をタイトル50文字、説明文500文字に正式決定する(2026-10-20 決定)
- 移動したカードは、移動先の列の一番上に入る(2026-10-20 決定)
- データ設計は、列(COLUMNS)を別テーブルにし、カードの並び順は「列に置かれた日時」で持つ(データ設計書のとおり)(2026-10-20 決定)
- ER図は、実際のDBを使って運用するところまで実装する。バックエンドを作る想定とし、マルチユーザー対応はしない。図はMermaid記法で書く(2026-10-20 決定)
- 要件定義書は概要とリンクだけにし、詳細は分野ごとの文書に分けて docs 直下に置く。技術スタックは今回は候補までとし、今後の課題で決める(2026-10-24 決定)
