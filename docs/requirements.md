## 1. プロジェクト背景・目的
### 1.1 背景
- AIエンジニアコース(スクール)の課題として、Trello風のタスク管理アプリを作る。
- 実在する顧客や発注者はいない。受講者本人が、依頼者・開発者・確認者を兼ねる。
- 仕事の進め方を学ぶため、実際の案件を想定した形式で要件定義書を作る。

### 1.2 目的
- **学習目的(主目的)**:要件定義から設計・実装・テストまでの一連の流れを経験し、システム開発の進め方を身につける。
- **成果物の目的**:Trello のような**カンバンボード形式**で、タスクの状態(未着手・作業中・完了)を視覚的に管理できるアプリを作る。
- やることをカードにして、列の間を動かし、進み具合を一目で分かるようにする。

### 1.3 学習で身につけたいこと
- 要件を整理し、文書にまとめる力
- 決めたことと決めていないことを区別して管理する力
- 要件とテストを対応づけて、完成を判断する力

## 2. 利用者・利用環境
- 利用者:自分1人(ログインや担当者の管理は不要)
- 環境:パソコンのブラウザ(Chrome など)のみ
- サーバーやデータベースは使わない(データはブラウザ内に保存する)

## 3. 用語
| 用語 | 意味 |
|---|---|
| ボード | 画面全体 |
| リスト(列) | To Do / Doing / Done の縦の列 |
| カード | 1つのタスク |

## 4. 機能要件(アプリができること)
| ID | 機能 | 内容 | 優先 |
|---|---|---|---|
| F-01 | 列の表示 | To Do / Doing / Done の3列を表示する | 必須 |
| F-02 | カード追加 | フォーム入力でカードを作り、To Do 列の**一番上**に入れる(新しいカードが上に並ぶ) | 必須 |
| F-03 | カード表示 | タイトル・優先度・期限を表示し、説明文も確認できる | 必須 |
| F-04 | カード移動 | ドラッグして別の列へ移す | 必須 |
| F-05 | カード削除 | 不要なカードを消す。削除前に確認ダイアログ(「本当に削除しますか?」)を出す | 必須 |
| F-06 | データ保存 | 再読み込みしてもカードが残る | 必須 |
| F-07 | 優先度の色分け | 高=赤、中=黄、低=緑 | 必須 |
| F-08 | 期限切れ表示 | 期限の**翌日以降**になったカードを赤字にする(期限当日は赤字にしない) | 必須 |
| F-09 | カード編集 | 作成済みカードのタイトル・説明文・優先度・期限を後から修正できる | 必須 |

### カードの項目
| 項目 | 必須 | 入力方法 | 備考 |
|---|---|---|---|
| タイトル | 必須 | 1行入力 | 空では追加できない |
| 説明文 | 任意 | 複数行入力 | |
| 優先度 | 必須 | 高・中・低から選択 | 初期値は「中」 |
| 期限 | 任意 | 日付選択 | |

## 5. ユースケース
利用者がシステムを使ってやりたいこと(目的)を一覧にし、手順を記述する。
データの保存(F-06)は利用者が直接行う操作ではないため、独立したユースケースにせず、UC-02〜05 の事後条件に含める。

### 5.1 アクター
| アクター | 説明 |
|---|---|
| 利用者 | アプリを使う自分1人。ログインや担当者の区別はない |

### 5.2 ユースケース一覧
| ID | ユースケース | 対応する機能要件 |
|---|---|---|
| UC-01 | ボードを見る | F-01、F-03、F-07、F-08 |
| UC-02 | カードを追加する | F-02 |
| UC-03 | カードを編集する | F-09 |
| UC-04 | カードを移動する | F-04 |
| UC-05 | カードを削除する | F-05 |

(F-06 データ保存は、UC-01 の事前条件および UC-02〜05 の事後条件として扱う)

### 5.3 ユースケース記述
#### UC-01 ボードを見る
| 項目 | 内容 |
|---|---|
| アクター | 利用者 |
| 目的 | タスクの状況を一目で把握する |
| 事前条件 | ブラウザでアプリを開いている |
| 基本フロー | 1. システムが保存済みのデータを読み込む<br>2. To Do / Doing / Done の3列を表示する<br>3. 各カードのタイトル、優先度、期限を、属する列に表示する<br>4. 優先度を色で示す(高=赤、中=黄、低=緑)<br>5. 期限の翌日以降のカードは、期限を赤字にする<br>6. 利用者がカードの説明文を確認する |
| 代替フロー | 1a. 保存データがない場合(初回など)は、カードのない3列を表示する<br>5a. 期限が当日、または未設定のカードは、赤字にしない |
| 例外フロー | なし(保存データの読み込み失敗は、非機能要件の検討で扱う) |
| 事後条件 | 最後に保存した状態のボードが表示されている |

#### UC-02 カードを追加する
| 項目 | 内容 |
|---|---|
| アクター | 利用者 |
| 目的 | やることを新しいカードとして登録する |
| 事前条件 | ボードが表示されている |
| 基本フロー | 1. 利用者がカード追加の入力を始める<br>2. タイトルを入力する(必須)<br>3. 説明文、優先度(初期値「中」)、期限を必要に応じて入力する<br>4. 追加を確定する<br>5. システムが To Do 列の一番上にカードを表示する<br>6. システムが内容を保存する |
| 代替フロー | 3a. 優先度を変えたい場合は、高・中・低から選ぶ |
| 例外フロー | 4a. タイトルが空の場合、システムは追加せず、入力を促すメッセージを表示する |
| 事後条件 | カードが To Do の先頭に追加され、再読み込みしても残っている |

#### UC-03 カードを編集する
| 項目 | 内容 |
|---|---|
| アクター | 利用者 |
| 目的 | 作成済みのカードの内容を直す |
| 事前条件 | 編集したいカードがボードに表示されている |
| 基本フロー | 1. 利用者が編集したいカードを選び、編集を始める<br>2. システムが現在の内容(タイトル、説明文、優先度、期限)を入力欄に表示する<br>3. 利用者が内容を修正する<br>4. 修正を確定する<br>5. システムがカードの表示を更新する(カードは今の列、今の位置のまま)<br>6. システムが内容を保存する |
| 代替フロー | 3a. 期限を消して、期限なしに戻す<br>3b. 編集をやめる場合は、キャンセルする(内容は変わらない) |
| 例外フロー | 4a. タイトルを空にして確定した場合は、更新せず、入力を促すメッセージを表示する |
| 事後条件 | カードの修正が反映され、再読み込みしても残っている |

#### UC-04 カードを移動する
| 項目 | 内容 |
|---|---|
| アクター | 利用者 |
| 目的 | タスクの進み具合に合わせて、カードの列を変える |
| 事前条件 | 移動したいカードがボードに表示されている |
| 基本フロー | 1. 利用者がカードをドラッグする<br>2. 別の列の上でドロップする<br>3. システムがカードを移動先の列の一番上に移して表示する<br>4. システムが内容を保存する |
| 代替フロー | 2a. 元の列にドロップした場合は、何も変わらない |
| 例外フロー | 2b. 列の外でドロップした場合は、元の場所に戻る |
| 事後条件 | カードが移動先の列にあり、再読み込みしても残っている |

#### UC-05 カードを削除する
| 項目 | 内容 |
|---|---|
| アクター | 利用者 |
| 目的 | 不要になったカードを消す |
| 事前条件 | 削除したいカードがボードに表示されている |
| 基本フロー | 1. 利用者が削除したいカードを選び、削除を始める<br>2. システムが確認ダイアログ(「本当に削除しますか?」)を表示する<br>3. 利用者が削除を承諾する<br>4. システムがカードをボードから取り除く<br>5. システムが内容を保存する |
| 代替フロー | 3a. 利用者が取りやめた場合は、カードは削除されず、そのまま残る |
| 例外フロー | なし |
| 事後条件 | カードが消え、再読み込みしても戻らない |

## 6. 非機能要件(機能以外の条件)
利用者は1人で、サーバーを使わない前提で、項目ごとに「数字にする」「簡単に扱う」「対象外」を判断した。

### 6.1 性能・拡張性
| ID | 項目 | 目標値 | 根拠 |
|---|---|---|---|
| NF-01 | 想定カード枚数 | 全体で200枚まで | 個人のタスクなら完了済みを含めても数十〜百数十枚。余裕を見て200 |
| NF-02 | 操作の反応時間 | カードの追加・編集・移動・削除が、200枚の状態でも1秒以内に画面へ反映される | 待たされたと感じない目安 |
| NF-03 | 起動時の表示時間 | アプリを開いてからボードが表示されるまで3秒以内 | 同上 |
| NF-04 | データ容量 | 200枚で約0.3MB以内(保存の上限は約5MB) | 1カード約1.2KB(タイトル50文字+説明文500文字、日本語は1文字最大2バイトで計算)×200枚=約240KB |

入力の上限(タイトル50文字、説明文500文字)は、NF-04 の計算に使う値で、データ設計書(data-design.md)で正式に決定した。

### 6.2 環境
| ID | 項目 | 目標値 |
|---|---|---|
| NF-05 | ブラウザ | Chrome の最新版(Windows)。他のブラウザは対象外 |
| NF-06 | 画面サイズ | 幅1280px以上のパソコン画面。スマホ・タブレットは対象外 |
| NF-07 | 導入 | インストール不要。HTML ファイルをブラウザで開くだけで使える |
| NF-08 | 画面構成 | 画面は1ページだけ |

### 6.3 使いやすさ
| ID | 項目 | 目標値 |
|---|---|---|
| NF-09 | 初めての操作 | 説明を見なくても、5分以内にカードの追加・移動・削除ができる(確認は作成者本人が行う) |

### 6.4 信頼性(異常系)
| ID | 項目 | 内容 |
|---|---|---|
| NF-10 | 保存に失敗した場合 | 容量超過や保存不可のときは、エラーを画面に表示する。表示中の画面は壊さない |
| NF-11 | 保存データが壊れていた場合 | 空のボードで起動し、その旨を表示する |

### 6.5 移行性・セキュリティ・運用保守(簡単に扱う)
| ID | 項目 | 内容 |
|---|---|---|
| NF-12 | データの保存先 | ブラウザの localStorage に保存する |
| NF-13 | データの引き継ぎ | バックアップや引き継ぎの機能は作らない。ブラウザのデータを消すとカードも消える(既知のリスク) |
| NF-14 | セキュリティ | ログインなし。データは端末内だけに保存し、外部へ送信しない。入力した文字は、そのままの文字として画面に表示する |
| NF-15 | 運用・保守 | 課題のため、運用や問い合わせ対応は行わない |

### 6.6 対象外とする項目(理由)
| 項目 | 理由 |
|---|---|
| 可用性(止まらず使えること) | サーバーがなく、自分のパソコンで動くため |
| 多人数での同時利用 | 利用者は1人のため |

## 7. 対象外(今回は作らない)
列の追加・名前変更、担当者、ラベル、検索、複数人での共有、同じ列内でのカードの並び替え、削除したカードの復元。
これらの機能追加は、基本機能が完成した後に改めて検討する。

## 9. 決定事項
- カード削除時は確認ダイアログを出す(2026-10-12 決定)
- カード編集(F-09)を機能要件に含める(2026-10-14 決定)
- 新しいカードは列の一番上に追加する(2026-10-14 決定)
- 期限切れは期限の翌日からとする(2026-10-14 決定)
- 完了条件は「F-01〜F-09 がすべて動くこと」とする(2026-10-14 決定)
- 課題のゴールは設計までとし、完了条件を「納品物が揃い、F-01〜F-09 が設計に反映されていること」に変更する(2026-10-18 決定)
- 納期は期限なし、スクールへの提出は不要(2026-10-18 決定)
- 非機能要件は NF-01〜15 のとおり数値化する。想定カード枚数は200枚、反応時間は1秒以内、起動表示は3秒以内、対応は Chrome 最新版・幅1280px以上、初めての操作は5分以内(2026-10-19 決定)
- 入力の上限(タイトル50文字、説明文500文字)は仮の値とし、P5(データ設計)で正式に決める(2026-10-19 決定)
- 同じ列の中でのカードの並び替えは作らない。列をまたぐ移動のみとする(2026-10-19 決定)
- 削除したカードを元に戻す機能は作らない(確認ダイアログがその代わり)(2026-10-19 決定)
- 説明文の確認、カードの追加・編集・削除の操作方法は、画面設計書(screen-design.md)の「3. 決定事項」のとおりとする(2026-10-20 決定)
- 入力の上限をタイトル50文字、説明文500文字に正式決定する(2026-10-20 決定)
- 移動したカードは、移動先の列の一番上に入る(2026-10-20 決定)
- データ設計は、列(COLUMNS)を別テーブルにし、カードの並び順は「列に置かれた日時」で持つ(データ設計書のとおり)(2026-10-20 決定)
- ER図は、実際のDBを使って運用するところまで実装する。バックエンドを作る想定とし、マルチユーザー対応はしない。図はMermaid記法で書く(2026-10-20 決定)
